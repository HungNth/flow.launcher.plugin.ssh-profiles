# Flow Launcher Node.js Plugin Development

Use this skill to create and maintain Flow Launcher plugins written in JavaScript or TypeScript. Flow is a Windows launcher, so generated plugins should behave well under Windows paths, PowerShell/manual install workflows, and Flow's local JSON-RPC invocation model.

Official docs summarized here:
- `plugin-dev`: non-.NET plugins communicate through JSON-RPC.
- `plugin.json`: every plugin needs a manifest in the plugin root.
- Node.js docs: Flow can run JavaScript/TypeScript plugins through Node.js, and releases should include dependencies so users do not run `npm install`.
- JSON-RPC settings docs: user-editable settings live in root `SettingsTemplate.yaml`.
- Plugin manifest repo: public store submissions require a release zip and a manifest PR.

Read `references/nodejs-plugin-reference.md` before scaffolding or changing a nontrivial plugin. Read `references/release-and-store.md` when the task includes packaging, GitHub Actions, GitHub Releases, or Plugin Store publication.

## Working Approach

1. Classify the task: new plugin, existing plugin change, bug fix, settings UI, release automation, or store submission.
2. Inspect the repository first. Preserve existing structure, package manager, module style, lint/test setup, icon naming, and release workflow unless there is a concrete reason to change them.
3. Clarify only high-risk missing details such as credentials, destructive actions, or a plugin name/action keyword that cannot be inferred. Otherwise choose conservative defaults and implement.
4. Keep Flow's user experience front-of-mind: query handlers must be fast, stdout must be valid JSON only, errors should become useful Flow results, and dependency/runtime assumptions should be explicit.

## Core Contract

Flow sends a JSON-RPC payload to the plugin entry file as a command-line argument. In Node.js this is normally parsed from `process.argv[2]`:

```js
const { method, parameters = [], settings = {} } = JSON.parse(process.argv[2]);
```

For `method === "query"`, return JSON on stdout in the shape:

```js
console.log(JSON.stringify({ result: results }));
```

Keep stdout reserved for the JSON response. Use `console.error`, file logging, or Flow-visible error results for diagnostics. Extra stdout text can break Flow's parser.

Typical result fields for Node.js JSON-RPC plugins:

```js
{
  Title: "Visible result title",
  Subtitle: "Secondary text",
  IcoPath: "Images\\app.png",
  score: 80,
  JsonRPCAction: {
    method: "open_result",
    parameters: ["https://www.flowlauncher.com"]
  }
}
```

Use `JsonRPCAction.method` either for a plugin method implemented by the entry file or for a documented Flow Launcher API method such as `Flow.Launcher.ChangeQuery`, `Flow.Launcher.ShellRun`, or `Flow.Launcher.ShowMsg`.

## Manifest Rules

Place `plugin.json` at the plugin root. Add the official schema URL when creating or materially editing the file:

```json
{
  "$schema": "https://www.flowlauncher.com/schemas/plugin.schema.json",
  "ID": "stable-uuid-here",
  "ActionKeyword": "kw",
  "Name": "Plugin Name",
  "Description": "Short user-facing description",
  "Author": "Author",
  "Version": "1.0.0",
  "Language": "javascript",
  "Website": "https://github.com/owner/repo",
  "IcoPath": "Images\\app.png",
  "ExecuteFileName": "main.js"
}
```

Do not regenerate `ID` for an existing plugin. Use `Language: "javascript"` for a JavaScript runtime entry. For TypeScript projects, prefer compiling to JavaScript and set `ExecuteFileName` to the built JS path unless the existing project deliberately ships a `.ts` entry and has been tested in Flow.

Use `ActionKeyword: "*"` only when the plugin should participate in global search. Global plugins need stronger scoring and filtering because they run more often.

## Project Shape

For simple JavaScript plugins, a lean structure is enough:

```text
plugin.json
main.js
package.json
package-lock.json
Images/app.png
SettingsTemplate.yaml   # only when settings are needed
```

For TypeScript or larger plugins, prefer:

```text
plugin.json
package.json
tsconfig.json
src/main.ts
dist/main.js            # generated by build
Images/app.png
SettingsTemplate.yaml   # only when settings are needed
```

If dependencies are required, include a lockfile and make the release workflow install dependencies before zipping. Avoid ESM-only packages and Node APIs newer than Flow's documented portable Node runtime unless you verify the current Flow runtime or bundle/transpile the plugin.

## Settings UI

When user-configurable settings are needed, create root `SettingsTemplate.yaml`. Its top-level object has a `body` array. Common setting types are `textBlock`, `input`, `inputWithFileBtn`, `inputWithFolderBtn`, `textarea`, `passwordBox`, `dropdown`, and `checkbox`.

Add the schema comment at the top:

```yaml
#$schema: https://www.flowlauncher.com/schemas/settings-template.schema.json
```

Use setting `name` values as stable keys read from the JSON-RPC `settings` object. Provide safe defaults in code even when the YAML defines `defaultValue`, because user settings can be missing or stale.

## Release And Store

When preparing a release, ensure:

- `Version` in `plugin.json` is the release source of truth.
- GitHub Actions installs dependencies, runs build/tests if present, zips the plugin with runtime files and `node_modules`, then publishes a GitHub Release tagged from `plugin.json`.
- The zip excludes `.git`, source-only clutter, local caches, test artifacts, and unrelated files.
- The release artifact includes `plugin.json`, the configured entry file, icons, settings template if present, and all runtime dependencies.

For Plugin Store submission, create a manifest PR to `Flow-Launcher/Flow.Launcher.PluginsManifest`. The manifest copies core metadata from `plugin.json` and adds `UrlDownload`, `UrlSourceCode`, and CDN-accessible `IcoPath`. See `references/release-and-store.md`.

## Verification

Run the repo's normal checks first (`npm test`, `npm run build`, lint/typecheck if present). Then smoke-test the JSON-RPC entry manually:

```powershell
node .\main.js '{"method":"query","parameters":["hello"],"settings":{}}'
```

Validate that stdout is parseable JSON and has a `result` array. If the plugin uses settings, run at least one payload with representative `settings`. If the plugin defines action methods, test their payloads separately and avoid surprising side effects during automated checks.

When Flow Launcher is available, test manual install with:

```text
pm install <local plugin folder, release zip URL, or local zip path>
```

## Final Response

Summarize the plugin language, entry file, action keyword, important files changed, and verification performed. If release/store work was requested, state the artifact name, tag/version, and manifest fields that still require real URLs or CDN icons.
